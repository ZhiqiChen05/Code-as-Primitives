Harnessing Frontier Models to Synthesize Low-Level Robotic Skills

Frontier-model agents can plan over skills. We target the skill itself: a harness that synthesizes low-level controllers as executable programs, without expert demonstrations. The model designs the policy class and refines it through simulation; the resulting controller runs without model calls.

01 / The idea

From invoking skills
to synthesizing them

A planner decides which skill to execute. A controller determines how to execute it. Frontier-model agents increasingly handle the first question, while assuming that the controllers behind those skills already exist.

Building those controllers remains a demanding part of robotics. Rotating a pen in a dexterous hand requires precise coordination of fingers and wrist, changing contacts, and rapid corrections before the pen slips. Such skills are typically supplied through hand engineering, expert demonstrations, or large-scale reinforcement learning. Automating controller synthesis addresses the bottleneck beneath high-level planning.

Code as Primitives enables frontier models to synthesize low-level robotic skills as executable programs, without expert demonstrations. During development, the model acts as a control engineer: it writes a controller, tests it in simulation, and improves it using feedback. Once synthesized, the program executes on its own, enabling low-latency control without a model call at every action.

Choose a policy class, then optimize within it

A basketball player first chooses a shooting form: stance, arm motion, release. Repeated shots then tune the release angle, force and timing against where the ball lands. If tuning stops helping, the player changes the form.

The same distinction appears in machine learning: choose a hypothesis space \(\mathcal F\), then optimize \(f^*=\arg\min_{f\in\mathcal F}\mathcal L(f)\). Here, the frontier model writes the policy class. Its program maps observations to low-level actions, with interpretable gains, thresholds and targets exposed as parameters. The model can design the parameter-search algorithm itself or use CEM, and can revise the policy class when the evidence calls for a different controller.

Make rollout evidence comparable

A long, noisy rollout can end in failure without revealing which part of the program should change. Rewriting both the control logic and its numerical settings after every attempt makes the outcomes difficult to compare.

Parameter search holds the policy class fixed within a search call. Tools such as optimize_policy evaluate batches of parameter vectors and summarize their behavior as scores and diagnostics. Each score belongs to a complete parameter vector. This produces compact, comparable evidence about specific parameter settings that guides the next candidates, while trajectories remain available for revising the controller itself.

A demanding test of low-level control

Our focus is the difficulty of synthesizing a skill, rather than exhaustive coverage of high-level task types. Dexterous hands provide a representative stress test: many coupled joints must coordinate under changing contacts. We study these challenges in DexVerse and Adroit, then examine what happens when controllers must coordinate longer sequences. The goal is a repertoire of reusable control primitives that robotic agents can eventually compose into larger tasks.

then let the program execute.
02 / The method

Controller synthesis
Simulation-guided refinement

Write a controller, test it in simulation, and improve it using feedback. Policy-class revision and optional parameter search work together before standalone execution.

Rewriting the whole policy after every rollout leaves many possible explanations for success or failure. A changed threshold and a completely different strategy are both possible edits. Testing a batch within one policy class gives the agent a more comparable set of outcomes.

The harness supports two ways to search. CEM (the cross-entropy method) is a built-in optimizer run by the host. Agentic search lets the model propose candidate batches, inspect their rollouts, and run its own numerical analysis with NumPy and SciPy. It also supplies reference texts for the task category. Computation tools do not themselves access the simulator; candidate evaluations are counted separately.

{·}

Core idea. The learned controller is a program, not a weight vector, so it is inspectable (a file you can read and diff), searchable (its constants are an explicit parameter space), and testable (the same frozen file runs from starts it has never seen).

Synthesizing a skill: reorienting a pen.

Contact-rich control makes both controller synthesis and refinement matter. In Adroit Pen, the controller sees the hand and pen state and must reorient the pen toward a target. An action that changes the pen’s orientation can also loosen the grasp or eject it, so a useful policy has to turn what it observes into a coordinated change across the fingers and wrist.

We follow one saved run, GPT-6 Astra with Agentic search on the ten-stage random-reset curriculum, through the learning loop. Figure 3 plays it alongside each stage of the loop.

Read the policy and evaluation contract

The core interface is select_action(observation). The program returns native actuator commands or joint-position targets, depending on the environment. In the evaluated policy-only modes, it executes without a model-provider request at each action.

Training acceptance and held-out testing are separate. Training evaluations can feed adaptation. Held-out starts are reserved for frozen evaluation, and their outcomes are not returned to the learning agent.

DexVerse: standalone execution across 75 tasks

We evaluate on 75 DexVerse tasks across six categories, including four long-horizon tasks. All tasks use state observations without expert demonstrations. Accepted controllers are frozen and evaluated on 50 unseen initial and target configurations per task, repeated twice. The same 50 configurations are used in both repeats, and tasks without an accepted controller count as zero.

On the 15 tasks with published imitation-learning baselines, Agentic search reaches 95.9% held-out success and CEM search reaches 96.7%, compared with 46.0% for the best imitation result on each task. On the remaining 60 tasks, Agentic and CEM search achieve 90.7% and 94.0%, respectively.

Adroit: 99.2% with random resets

GPT-6 Astra achieves 99.2% held-out success: 119 successful episodes out of 120. With reasoning set to max, the model learns Door, Hammer, Pen, and Relocate without expert demonstrations. Each task uses one ten-stage curriculum with fresh native simulator resets throughout learning, Agentic parameter search, and training validation. The final controllers execute from state observations, with no model calls in the control loop.

  1. Learn across fresh starts. Every learning reset and independent search rollout receives a new host-sampled seed. Accepted policy code and eligible public evidence carry forward into the next stage, which has a fresh context and budgets.
  2. Increase the acceptance requirement. At stage k, one frozen policy must succeed on all k fresh validation episodes in a single submission. A failed submission may be revised and retried on new seeds while budgets remain. All four tasks passed all ten stages.
  3. Freeze, then test. The outgoing stage-ten controller runs on 30 additional seeds per task, reserved before adaptation and disjoint from every training seed. All 120 tests completed with zero model calls, zero execution errors, and no interrupted replacements.

Exact Adroit acceptance rule and evaluation settings

These experiments use the native Gymnasium-Robotics Adroit tasks in simulation, with state vectors of 39–46 values and the full 24–30 actuator commands. Each episode allows 200 native actions at 100 Hz. At episode completion, success requires more than 25 successful frames for Door, Hammer, and Relocate, or more than 20 for Pen. Frames need not be consecutive, and an early successful frame does not end an episode.

Native per-step criteria are a door hinge angle of at least 1.35 radians; nail-to-goal distance below 0.01 m; pen position error below 0.075 m with an axis dot product above 0.95; and relocated object-to-target distance below 0.1 m. The only held-out failure was Door episode 22 (seed 489500068), which reached the 200-step limit without a successful frame.

Each training stage permits up to 300 model requests, 1,000 tool calls, 100 learning resets, 250 frozen submissions, 20,000 search rollouts, and 12 hours of stage time. Exhausting a stage budget ends the chain. Door used 16 validation submissions across ten stages; Hammer used 10, Pen 13, and Relocate 10. Their respective validation episode totals were 85, 55, 68, and 55.

There is one training chain per task, and independent held-out evaluation exists only for the final checkpoint. Training-stage acceptance is not a held-out learning curve. The result concerns native simulator reset distributions; it does not measure arbitrary physical disturbances or real-world transfer. Exact protocol, seed ledgers, and source hashes ↗

Earlier fixed-start curriculum: 48.3% versus 99.2%

An earlier GPT-6 Astra campaign learned ten fixed starts in sequence and required each accepted controller to solve the entire prefix introduced so far. Its final controllers succeeded on 58/120 held-out episodes (48.3%), compared with 119/120 (99.2%) for the fresh-reset curriculum. Both used ten stages and the same nominal stage limits.

This is a descriptive campaign comparison. Reset protocol, guidance, held-out seed sets, and realized interaction costs differ, so the observed gain does not isolate the causal effect of random resets. Both evaluations use simulated native reset states; neither provides replication across independent training chains.

The Claude Opus 5.5 Agentic-versus-CEM results below come from a separate campaign. They retain their own training protocol and outcomes; the 99.2% result above belongs specifically to GPT-6 Astra with the ten-stage random-reset curriculum.

Both searches produce controllers that generalize. Across the 66 DexVerse tasks shown, mean held-out success is 94.4% for Agentic search and 96.0% for CEM search; 49 and 48 tasks respectively score exactly 100%. Per task the two are evenly split: Agentic search is higher on 10 tasks, CEM search on 10, and the rest tie. Among the 64 accepted Agentic controllers, mean success is 97.3%; the 94.4% figure above also includes the two tasks without accepted controllers. The gaps are largest in Articulation (81.0% vs. 86.7%), where Agentic search has no accepted policy for OpenHuaweiPhone and neither arm solves OpenGlasses.

On Adroit, both reach 100% on Door. CEM search also reaches 100% on Hammer and Relocate, while Agentic search reaches 93.3% and 66.7%. With 30 starts per task and one training chain per search mode, a single Adroit comparison is a small sample.

Cost is where the two differ. On DexVerse, the median task costs 81 rollouts with Agentic search and 5.5 with CEM search. In 54 of the 66 tasks, the first controllers designed under CEM search pass the training starts after resets alone, without a single search rollout; under Agentic search that happens in 7. Mean cost per task is 154.9 rollouts for Agentic search and 65.9 for CEM search.

The pattern is not uniform. On Adroit Hammer, CEM search spends 1,063 rollouts where Agentic search uses 93, and on DexVerse SqueezeScissors CEM search spends 1,756 to Agentic search's 966 while reaching lower held-out success (68% vs. 99%). A fixed optimizer is cheap when the first design is close; on these two tasks, the Agentic search reached an accepted controller with fewer rollouts.

Scope. These are simulation results with state observations and one training chain per task and arm. Every number comes from the campaign reports, and every video below is a replay of a recorded held-out episode.

The failures are concentrated. Of the 66 DexVerse tasks, Agentic search falls below 90% held-out success on eight: OpenHuaweiPhone and OpenGlasses (not accepted), RelocateObject (58%), FunctionalPourCan (69%), UnscrewCap (78%), PourMugPickUpStick (78%), BimanualLiftBasket (87%) and OpenFlatFolder (88%). Four of them (UnscrewCap, OpenFlatFolder, OpenHuaweiPhone and RelocateObject) are also among the six most expensive Agentic searches.

Cheap acceptance is not the same as a robust policy. FunctionalPourCan is accepted by Agentic search after only 21 rollouts but succeeds on 69% of unseen starts; CEM search reaches 100% on the same task. A short search does not by itself show that the controller is robust.

04 / Limits and longer tasks

Where refinement
remains difficult

Pen manipulation and long-horizon tasks expose the cost of coordinating contact, recovery, and multiple stages of behavior.

A benchmark pass can hide a brittle skill.

An earlier fixed-start Pen prototype switched between two control vectors using the pen’s observed axis. On its recorded training start, it accumulated 35 successful frames—enough to pass the aggregate benchmark criterion—then dropped the pen at step 69.

The newer random-reset policy behaves differently in the shown held-out replay: its last 121 frames are continuously successful, and it finishes with the pen retained and aligned. All 30 final held-out episodes end on successful frames.

The earlier prototype passed 2/9 additional seeds; the final random-reset policy passed 30/30 reserved seeds. These are different campaigns, protocols, and sample sizes—not a controlled ablation. The videos illustrate behavior beyond the binary score.

Pen remains expensive to learn. The random-reset run used 6,095 search rollouts and 1,233,120 adaptation environment steps, compared with 875 search rollouts for Hammer.

Composing skills over longer horizons

The four long-horizon tasks in the paper reach 39.8% held-out success with Agentic search and 63.2% with CEM. These are substantially below the results on the shorter tasks. The complete category breakdown is in Section 3.

DexVerse’s long-horizon tasks combine manipulation and articulation. CookFoods asks the hand to position a pot, place ingredients, pour from two vessels, and operate a stove. OvenBakeSalmon uses two hands to season the salmon, open the oven, load the tray, close the door, and turn a knob.

Completion can depend on earlier conditions still holding: the pot and ingredients must remain correctly placed, or the salmon must remain inside the oven. A controller must coordinate the full task, not just produce an isolated successful motion.

The hand must first lift the mug off its tree, then pour milk over it, set it under the espresso machine, and turn the machine’s switch. Both frozen policies start from the same unseen state, held-out seed 9000, and both succeed.

Comments on long horizons

Our method focuses on synthesizing reusable low-level robotic skills. We view parameter search as a tool for refining these local controllers, rather than optimizing an entire long-horizon execution. For composite tasks, we envision handling uncertainty through a higher-level policy that selects and composes primitives as the state evolves, without rerunning parameter search each time a primitive is used. The goal is to reuse these atomic policies across longer tasks and continually improve the primitives themselves using feedback from execution.
